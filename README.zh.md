# dsh-work-diary

[English](README.md) | 中文

DSH Web GUI 的每日工作日记。侧边栏多一个「日记」图标，点开按天汇总当天有活动的会话，生成一份 Markdown 日记；可每天定时生成，也可随时手动生成，用来总结的模型可配置。

一天开十几个会话、跑几十个工具调用，到下班往往想不起今天到底做了什么。这个插件替你把这些会话翻一遍，攒成一篇能看的日记——不读全文，够说明「大致做了什么」就行。

## 做什么

- 按本地时区挑出某一天有活动的会话（默认今天，可切昨天或任意日期）。「有活动」按最近一次真人提问判定，跨天继续干的长会话不会漏。
- 一个会话常常跨好几天，所以事件先按天切一遍：只保留目标日期本地 00:00 到次日 00:00 之间的轮次，别的日子干的活一律不送。日记写的是「这一天」。
- 每一轮送两行：真人诉求（前 50 字）+ 这一轮的 AI 结论（前 200 字）。轮次 = 一条真人输入 + 它之后到下一条真人输入之前那条「给用户的结论」，中间跟着工具调用的助手消息是内部过程，全部丢弃。超过「每会话抽取轮次」（默认 50）时按首 25% / 中 50% 均匀抽样 / 尾 25% 取样。
- 生成按项目拆开：先按 `cwd` 分组，每个项目发一次请求写该项目的段落，全部返回后再发一次请求合并成完整日记（含「今日概览」）。当天只有一个项目时退化成一次请求。
- 模型按固定节输出：今日概览 / 按项目列出今天做了哪些工作；完整档多一节遗留与下一步。
- 面板下方始终列出当天会话，点卡片直接跳到对应会话。

## 安装

从 npm 安装，或从任何收录了它的插件市场安装：

```sh
dsh plugin --profile web add @smwyylc/dsh-work-diary
```

或把源码目录作为本地 bundle 安装：`lib/index.js` 是 Host 半边，`lib/client.js` 是 Client 半边，`cordis.patch.yml` 声明要挂载的行，`icon.svg` 是侧栏图标，没有构建步骤。

1. 把本目录放到任意位置（和其他插件放在一起即可）。
2. 用 DSH 插件管理器的「安装本地 bundle」把它装入当前 profile。这一步会写好 profile 的依赖项与挂载，不用手改 profile。
3. 重启 DSH，侧边栏出现「日记」图标。

改代码后需要重启才生效：模块在进程启动时加载。

## 用法

1. 侧边栏点「日记」图标。
2. 顶部选日期（今天 / 昨天 / 日期框），点「生成总结」，正文流式出现。多项目的一天会先显示「正在分项目生成（2/5）…」的过渡稿，全部写完后再换成正式日记。
3. 要改定时、模型或抽样轮数：点右上角「设置」，内联展开设置区，改完点「保存设置」。

已有总结的日期，按钮是「重新生成」——每点一次都是一次真实的模型调用。
模型输出撞到长度上限时，正文下方会标出来，那一次的结尾可能是半句话。

## 预计花费

口径：**输入 = 当天的轮次记录（每轮用户输入 50 字 + AI 结论 200 字）+ 每次请求的固定模板**；**输出 = 每个项目一次请求 + 一次合并请求**（当天只有一个项目时只有一次请求）。读会话、切轮次都是本地磁盘 I/O，不花 token。

| 项 | 精简（默认） | 完整 |
| --- | --- | --- |
| 输入 token（14 会话、296 轮的一天，抽到 171 轮） | 约 20.8k | 约 21k |
| 单次请求的输出 + 思考 | 约 2600 | 约 2600-3000 |
| 请求次数 | 项目数 + 1（单项目时 1 次） | 同左 |

一天合计约等于「输入 + 单次输出 × 请求次数」。实测最忙的一天（14 个会话、296 轮，抽到 171 轮）光输入就约 20.8k token；项目数按 6 个估算，合计约 3.8 万 token。只有一两个项目的清闲日约 8000-11000 token。

相比上一版（整份日记一次请求、约 9000-11600 token）这一版明显更贵，原因是两件事叠加：输入从「每会话首尾两条」变成「当天每一轮都送一些」，涨了约 3 倍；输出侧的思考在每个请求上都要重付一遍，请求数越多总价越高。换回来的是日记终于能答上「中间到底做了什么」。想压成本：把「每会话抽取轮次」调小，或者关掉定时只按需生成。

## 省 token 的做法

从取样到输出逐层压，每一层只留「答得出今天做了什么」所需的部分。

**取样**：一个会话送当天的轮次，每轮两行（用户诉求 + 该轮 AI 结论）。

- 先按天切。一个会话常常跨好几天，只保留目标日期本地 00:00 到次日 00:00 的事件——「今天做了什么」不该混进前几天的收尾。时间戳字段是事件自带的毫秒或 ISO 时间。
- 轮次的定义：一条真人输入（`source.kind === 'user'` 的 `user/message`，agent 注入的上下文不算）+ 它之后到下一条真人输入之前的那条 AI 最终回复。判据是「后面不紧跟 `tool/call`」：一轮里 DSH 会连着产生好几条助手消息，每条后面跟一批工具调用，那些是内部过程，占了日志九成体积，进摘要只会把真正的结论挤掉。判据在按天过滤后的序列上判断——跨天会话在当天末尾的那条助手消息，本来就该算当天的结论。
- 结论只收 `text` 块，`reasoning`（思考过程）永远不进摘要——「想过」不等于「做过」。
- 超量时按固定比例抽样：首 25% 全取、中 50% 均匀抽样、尾 25% 全取。中间那段不能连续取——话题转折往往就在中段，连续取 26 条等于只看当天某几个小时；按间隔跳着取能保住「这一天怎么演变的」。不足上限的全量送，不抽样。抽了多少会写在会话头里（`- 13:05-17:40 · 175 轮（抽 50 轮）`），免得模型把没送的中间段读成空白。抽样在切完轮次时就做掉，只有抽中的轮次留在内存里，会话头报的仍是真实总轮数。
- 每轮截断：用户输入前 50 字、AI 结论前 200 字。用户输入一句话就说完；结论 200 字基本覆盖「做成了什么」，而一条完整答复常有上千字，整条送进去等于把额度花在细节上。两个额度是固定的，不随详细程度变——档位只该改输出详略，不该偷偷改输入口径。
- 客套、追问、整段粘贴的代码或日志不占「用户: 」这一行，但**这一轮不丢**：AI 结论照样送，「继续」之后那条结论往往正是这一轮的实际产出。判据：
  - 整句只由客套词拼成（去掉标点后只剩「好的 / 谢谢 / 继续 / ok / thanks」这类）才算客套；
  - 短追问要三条同时成立才丢：疑问性开头（「所以 / 那 / 然后 / 是不是」）、疑问语气收尾、不足 20 字。避免误杀「帮我把并发降到 4？」这种真指令；
  - 整段代码：首词是 `const` / `function` / `select` / `import` 之类并且近处出现语句标点，或者多行带分号花括号。只看首词会把「delete the temp files」这种正常句子误判成代码；
  - 整段粘贴的日志或命令：长度 60 字以上而中文占比不足 25%。真诉求是中文句子，日志、报错栈、curl 命令几乎纯 ASCII，两边分得很开。
  - 标题另有一套判据，只排代码与过长粘贴，短标题（「git 版本」）照常保留——否则摘要头会全退化成项目名，分不出会话。
- 不再送「碰过的文件名」。它是上一版在只送首尾两条时补信息量的权宜之计；现在每轮都有正文，文件列表反而占位置。

**输出**：

- 按项目拆请求。先按 `cwd` 分组（同一目录下不同会话算一个项目），每个项目一次 `llm.stream`，并发 3；全部返回后再发一次合并请求，写「今日概览」并把各段串起来。只有一个项目时退化成一次请求，不白付一次思考。单个项目的请求失败只丢那一段并记日志，不拖垮整份日记。合并请求是最后一步，返回空内容时会用 1.5 倍的 `maxTokens` 重试一次——它一挂，前面写好的每个项目段落全作废。
- 请求带 `maxTokens` 硬顶（精简 4000 / 完整 6000）。这个额度必须**同时装下思考与正文**：2026-10-28 实测八个模型在 900 额度下全部返回空正文，因为它们的思考长度在 1500-9000 字之间波动，额度在吐出正文前就被吃光。字数约束仍然写在提示词里（单项目段落精简 300 字 / 完整 400 字，合并后总长精简 600 字 / 完整 800 字）；4000 额度下实测正文落在 720-1000 字之间，基本服管。
- 思考在这个网关上关不掉。2026-10-28 试过六种写法（`reasoning_effort=none/low/minimal`、`enable_thinking=false`、`thinking.type=disabled`、以及什么都不传）：网关全部照收不报错，也一个都不转发，思考最短仍剩约 460 字；而 `reasoning_effort=none` 在真实 digest 上有时反而让思考涨到 6536 字。唯一还能抓的抓手是提示词，现在已明确禁止输出思考、分析与草稿过程——受控实测中这让正文从「空」变成 905 字。所以思考是输出成本里更大的一半，也是分开按项目请求后总价上涨的主因。

## 配置

设置保存在 `[DSH_HOME]/work-diary/settings.json`（`DSH_HOME` 未设置时为 `~/.dsh`）。字段：

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `enabled` | `true` | 是否每天定时自动生成 |
| `time` | `18:00` | 本地时间 HH:MM，到点自动跑一次 |
| `provider` | 空 | 总结模型的 provider；provider 与 model 都为空表示跟随默认模型 |
| `model` | 空 | 总结模型的 model |
| `language` | `zh` | 输出语言，`zh` 或 `en` |
| `verbosity` | `brief` | 详细程度：`brief` 精简（省 token）/ `full` 完整 |
| `maxSessions` | `40` | 单次总结最多纳入多少个会话，超出的在面板上提示数量 |
| `roundsPerSession` | `50` | 单个会话最多送多少轮；超出时首 25% / 中 50% 均匀抽样 / 尾 25% 取（比例固定，不可配） |

设置面板里可以改开关、时间、provider / model、语言、详细程度、每会话抽取轮次；`maxSessions` 需要手改 `settings.json`，改完下次启动生效。`roundsPerSession` 填非数字或留空时回退默认 50，数字会被夹在 1 到 200 之间。

自动执行：到点对当天跑一次（面板状态显示「自动」）。DSH 启动时若当天还没有结果、且当前时间已过设定时间，会立即补跑一次，Host 日志里能看到 `catch-up` 字样。

生成结果按日期保存在 `[DSH_HOME]/work-diary/last-runs.json`，保留最近 30 份。打开面板时该日期已有结果就直接显示，不会重复生成。

## 数据从哪来

- 会话清单取两路并集：`sessionController.list()` 里 `updatedAt`（最近一次真人提问，取自持久化投影缓存）落在当天的会话，加上最近 7 天创建的会话。投影缓存不是全覆盖，没覆盖的会话 `updatedAt` 会退回创建时间而被漏掉，第二路就是补这个漏；最后用真实事件时间终审。第二路是纯追加，猜错只会多读几个会话，不会漏。
- 事件走 `sessionQuery.observeSession` 读，没有它的 DSH 版本退回 `sessionQuery.readSession`。换的原因是旧路径太贵：`readSession` 每读一次都先列举整个持久化存储，再把每个事件深拷贝两遍（加载时一遍、`snapshotSessionEvent` 里再一遍），还要建一个会话对象——35 个会话实测 137 秒，期间界面近乎冻结。`observeSession` 只对单个会话做定向 stat，事件是冻结共享的引用而不是副本，缓存 5 条 LRU，返回的 lease 要求用完即 dispose（本插件读完事件就归还）。
- 每个会话只读一次：一次拿齐 header、标题、计数和当天的轮次。两次会话之间会让出一次事件循环，长时间收集不会再饿死 HTTP 服务与界面渲染。
- 事件按 `dayBounds` 切一遍（本地 00:00 到次日 00:00，当天则截到当前时刻），只保留目标日期的事件；当天的真人输入一条都没有的会话直接跳过，不占名额也不进 digest。
- 轮次 = 真人输入 + 该轮的 AI 最终回复。真人输入只认 `source.kind === 'user'` 的 `user/message`；AI 最终回复取 `assistant/message` 的 `data.message.content`（注意不是 `data.content`，那是用户消息的路径），块数组里只收 `type === 'text'` 的块并用换行拼接，且这条消息后面不能紧跟 `tool/call`。
- 标题取 `session/title` 事件（last-wins，与官方 title 投影一致）；标题是代码或过长粘贴时退回项目名。
- 生成走 `llm.stream` 流式接口；模型由设置决定，留空则跟随 `agentDefaultModel`。轮次数组只在 Host 内部用，`collect` / `poll` 回给面板的是切掉轮次正文的摘要，不重复传输几十 KB。
- 同一天的并发收集会合并成一次；过去日期的结果直接缓存复用，当天的只信 5 分钟。面板先读落盘的总结，再后台收集会话清单。内存里最多保留 8 份运行记录。
- 单个会话读取失败只跳过该会话并记一行日志，不影响整次总结。
